# AGENTS.md

This file provides guidance to AI agents when working with code in this repository.

## Context

GuildKit is a Next.js App Router application built and served by [vinext](https://vinext.dev), a reimplementation of the Next.js APIs on Vite. It follows the directory structure of Next.js, but the `next` package is not installed.

#### Key Directories

- **projects/guildkit/src/app** - Next.js pages and API routes using app directory
- **projects/guildkit/src/lib** - Business logic, type definitions, and utilities
- **projects/guildkit/src/components** - Reusable React components
- **projects/guildkit/prisma** - Database schema, migrations, and model definitions
- **projects/guildkit/public** - Static assets and vendor files

### Architecture

- GuildKit is built as a Next.js-based web application. It uses vinext instead of Next.js to build and serve the app. `next/*` imports are provided by vinext, and the types come from `vinext typegen` (`next-env.d.ts`).
- **Runtime**: The app runs on Cloudflare Workers (workerd), including `pnpm run dev` and `pnpm run preview` on local machines through `@cloudflare/vite-plugin`. Server code reads environment variables via `process.env`, and each variable must be declared as a binding in `cloudflare.config.ts`. Workers do not allow reusing an I/O object (e.g. a DB connection) across requests, so `src/lib/prisma.ts` does not keep connections in the pool.
- **Prisma clients**: `src/lib/prisma/` is generated for the Workers runtime and used by the app. `src/lib/prisma-node/` is generated for Node.js and used by the scripts running on Node.js such as seeding.
- GuildKit uses [Prisma](https://www.prisma.io/docs/) as the ORM.
- GuildKit uses an S3-compatible object storage. It uses [`@aws-sdk/client-s3` npm package](https://www.npmjs.com/package/@aws-sdk/client-s3).
- GuildKit uses Podman Compose, which is compatible with Docker Compose, to run the database and object storage server on the local development machines.
- GuildKit uses pnpm instead of npm.
- Tasks are npm scripts in each `package.json`. Tasks that need a script file put it under `scripts/` of each project, and the npm script runs it with `jiti` (TypeScript) or `nu` ([Nushell](https://www.nushell.sh)). Nushell is installed from npm. [mise-en-place](https://mise.jdx.dev) only installs Node.js, runs `pnpm install`, and loads `.env`.
- **Instance config**: `guildkit.config.ts` at the repo root is the per-instance user config. `src/lib/configs.ts` imports it, defines the `GuildKitConfig` type, and applies defaults. Client code must use `src/intermediate/public-configs.json` instead of importing the config.
- **Storage**: `src/lib/storage.ts` builds an S3 client for each `storage.platform` (`development` → local RustFS with hard-coded credentials, `cloudflare` → R2, `minio`, `rustfs`, `aws`, `custom`).
- **Auth**: better-auth with the organization plugin. The server instance is in `src/lib/auth.ts`, and the client is in `src/lib/auth/client.ts`. Users have a `type` (`candidate` | `recruiter`) and a `role` (`src/lib/auth/roles.ts`). Recruiters belong to organizations.
- **Auth guard**: Server components and actions call `requireAuthAs("recruiter" | "candidate" | "any", options)` from `src/lib/auth/server.ts`. It redirects unauthenticated users to `/auth`, redirects users with no type to `/auth/signup`, returns a `GuildKitError` for recruiters who have no organization, and sets the active organization. Callers read `session.activeOrganizationId` from the result.
- **Mutations**: Server actions in `src/lib/actions/` have the `useActionState` signature `(prevState: ActionState<T>, formData) => Promise<ActionState<T>>`. They validate input with Zod schemas from `src/lib/validations/` and return `{ errors: flattenError(error) }` when validation fails.
- **Component split**: Interactive components are split into `X.tsx` (server) and `X.client.tsx` (client), e.g. `JobEditor`, `OrgEditor`, and `app/auth/page.client.tsx`.
- **Errors**: Thrown errors include a unique code such as `GK-9JFB6` to make them traceable.

### Quick Start

1. `cp .env.example .env` (required: setup scripts need `SERVER_ENV`)
2. Start the Podman daemon
3. `mise install`
4. `pnpm run build`
5. `pnpm run dev`

### Commands

Run tasks with `pnpm run <script>` in a shell where mise is activated, or with `mise exec -- pnpm run <script>`, so that the tools and `.env` from `.mise/config.toml` are loaded. Root scripts (`dev`, `build`, `preview`, `deploy`, `deploy-preview`, `test`, `lint`, `fix`, `sync`) run the same-name script in each project with `pnpm run -r --if-present`. pnpm does not install the dependencies before running scripts (`verifyDepsBeforeRun: warn` in `pnpm-workspace.yaml`), so run `pnpm install` when it warns that `node_modules` is out of sync.

- `mise install` - Install all dependencies, including npm dependencies. `pnpm install` runs the root `prepare` script, which starts the containers and then runs `sync` to create the generated files. pnpm skips `prepare` when `node_modules` is already up to date, so do not rely on it to create the generated files.
- `pnpm run dev` - Start dev servers including application server, database server, and object storage server.
- `pnpm run build` - Build application with `vite build`.
- `pnpm run preview` - Build application in the `development` mode and serve the build output on the local workerd runtime.
- `pnpm run deploy` - Run `scripts/deploy.nu`. It deploys the build output to Cloudflare Workers (production), then applies the migrations (`prisma migrate deploy`) and seeds the DB (`prisma db seed`). Run `pnpm run build` first.
- `pnpm run deploy-preview` - Run `scripts/deploy-preview.nu` for the preview workflow. It deploys the build output as a Cloudflare Worker Preview named after the PR author's GitHub username in `PR_AUTHOR` (without a trailing `[bot]`), so each user has a fixed Preview URL (`cf previews deploy --prebuilt`). Then it sets the Preview's `DATABASE_URL` and `BETTER_AUTH_URL` secrets (`wrangler preview secret bulk`), applies the migrations (`prisma migrate deploy`), seeds the DB (`prisma db seed`), and comments the Preview URLs on the PR `PR_NUMBER` (`gh pr comment`). Run `pnpm run build` with `CLOUDFLARE_PREVIEW_BUILD=true` first, so that the build output is a Preview build. It also requires `DATABASE_URL` and `GH_TOKEN`.
- `pnpm run lint` - Run `tsc --noEmit` and ESLint.
- `pnpm run fix` - Fix linting issues.
- `pnpm run clean` - Delete the Docker containers and gitignore'd files except for .env and mise.local.toml.
- `pnpm run refresh` - Recreate the Docker containers and pnpm-lock.yaml, and update pnpm.
- `pnpm run ai-postedit` - Syncs generated files, then runs the project lint scripts, `tsc --noEmit`, `eslint --fix`, and the project fix scripts. Use it to check your edits.
- `pnpm run sync` - Generates the currency list if it does not exist, regenerates the Prisma clients, better-auth schema, and vinext type definitions. When `SERVER_ENV` is `development`, it also applies migrations (`prisma migrate dev`) and seeds dev data. Run it at the root or in `projects/guildkit`. The `dev`, `build`, `lint`, and `fix` scripts of `projects/guildkit` all run it.
- `pnpm run seed` (in `projects/guildkit`) - Seeds the DB. It only runs when `SERVER_ENV` is `development`, `demo-production`, or `demo-preview`, and only when the DB is empty.

There is no test suite yet. The root `test` script exists, but no project defines a `test` script.

### Environment variables

- `SERVER_ENV` is required by the setup and sync scripts. Copy `.env.example` to `.env` for local development (`SERVER_ENV=development`). mise loads `.env` automatically.
- On Cloudflare Workers, set the secrets declared in `cloudflare.config.ts` as the Worker's secrets. `SERVER_ENV` is not a secret: `cloudflare.config.ts` embeds it into the Worker as `demo-preview` for Preview builds (`pnpm run deploy-preview`) and `demo-production` for the other builds. In the `development` mode (`pnpm run dev` and `pnpm run preview`), it is loaded from `.env`. `cloudflare.config.ts` embeds `BETTER_AUTH_URL` as `https://demo.guildkit.net` only in the `production` mode and only when the build is not a Preview build. Otherwise it is a secret, loaded from `.env` in the `development` mode. Worker Previews take their secrets from the Preview base config, and `pnpm run deploy-preview` sets the PR's Neon branch as `DATABASE_URL` and the Preview URL as `BETTER_AUTH_URL` of each Preview. Since the Worker cannot start without `BETTER_AUTH_URL`, `pnpm run deploy-preview` sets a dummy `BETTER_AUTH_URL` in the Preview base config and the existing Preview before the deployment. `pnpm run deploy-preview` requires `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`.
- In `development`, the root `prepare` script starts Postgres and RustFS (an S3-compatible store) with `compose.yaml`. The RustFS image built from `containers/storage/Dockerfile` already has the `guildkit` bucket. The RustFS console is at http://localhost:9001.

## Instructions

- Wording: An **organization** is the hiring company. A **recruiter** is a staff user who belongs to an organization. Use **employer** only when you mean both.
- Use the `@/` path alias for `projects/guildkit/src`, and include the `.ts`/`.tsx` extension in import paths.
- Do not edit gitignored files.
- After you update the code, check AGENTS.md and find if there is anything outdated. If there is any outdated content, update or delete it.
- Split Git commits by step. Keep each commit's diff readable: if stylistic changes (formatting, renames, reordering) would make the diff hard to read, put them in separate commits from the functional changes.
- When you rebase onto the `main` branch, do not fold the changes needed to adapt to `main` into the existing commits. Put them in separate new commits so that the user can fixup them into the original commits later.
- Commit changes to the following files in separate commits from other changes:
  1. Lock files of the package managers (e.g. `pnpm-lock.yaml`, `skills-lock.json`)
  2. The `allowBuilds` section of `pnpm-workspace.yaml`
  3. Database migration files
  4. Other machine-generated files
