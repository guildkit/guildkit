# AGENTS.md

This file provides guidance to AI agents when working with code in this repository.

## Context

GuildKit is a pnpm monorepo. The frontend is a Next.js App Router application, and the backend is an API-only Next.js application (Route Handlers only). Both are built and served by [vinext](https://vinext.dev), a reimplementation of the Next.js APIs on Vite, on Cloudflare Workers. They follow the directory structure of Next.js, but the `next` package is not installed.

#### Key Directories

- **projects/backend/prisma** - Database schema and model definitions
- **projects/client/src** - API client used by the frontend
- **projects/shared/src/zod** - Zod schemas shared by the backend and the frontend

- **projects/guildkit/public** - Static assets and vendor files

### Architecture

- The frontend (`projects/guildkit`) is a Next.js application. It calls the backend through `@guildkit/client`.
- The backend (`projects/backend`) is an API-only Next.js application, run with vinext (`vite dev`, `vite build`) and deployed to Cloudflare Workers with `cf deploy`.
- Both use vinext instead of Next.js to build and serve the app. `next/*` imports are provided by vinext, and the types come from `vinext typegen`.
- **Runtime**: The frontend and the backend run on Cloudflare Workers (workerd), including the dev servers on local machines through `@cloudflare/vite-plugin`. Server code reads environment variables via `process.env`, and each variable must be declared as a binding in `cloudflare.config.ts` of the project.
- **Prisma clients**: `projects/backend/src/lib/prisma/cloudflare/` is generated for the Workers runtime and used by the backend. `projects/backend/src/lib/prisma-node/` is generated for Node.js and used by the scripts running on Node.js such as seeding.
- GuildKit uses [Prisma](https://www.prisma.io/docs/) as the ORM.
- GuildKit uses an S3-compatible object storage. It uses [`@aws-sdk/client-s3` npm package](https://www.npmjs.com/package/@aws-sdk/client-s3).
- GuildKit uses Podman Compose, which is compatible with Docker Compose, to run the database and object storage server on the local development machines.
- GuildKit uses pnpm instead of npm.
- **Workspace dependencies**: `pnpm run -r` runs the scripts in the order of the workspace dependencies: `@guildkit/shared`, `@guildkit/db`, `@guildkit/backend`, `@guildkit/client`, and the frontend. pnpm refuses cyclic workspace dependencies, so `@guildkit/db`, which imports the `PrismaClient` type from `@guildkit/backend/prisma`, resolves `@guildkit/backend` through the root `package.json` instead of its own.
- Tasks are npm scripts in each `package.json`. Tasks that need a script file put it under `scripts/` of each project, and the npm script runs it with `jiti` (TypeScript) or `nu` ([Nushell](https://www.nushell.sh)). Nushell is installed from npm. [mise-en-place](https://mise.jdx.dev) only installs Node.js, runs `pnpm install`, and loads `.env`.
- **Instance config**: `guildkit.config.ts` at the repo root is the per-instance user config, typed with `GuildKitConfig` from `@guildkit/shared/zod`. The backend reads it via `projects/backend/src/lib/config.ts`.
- **Storage**: `StorageClient` in `projects/backend/src/lib/storage.ts` builds an S3 client from `servers.storage` in the instance config (local RustFS in development, Cloudflare R2 otherwise).
- **Auth**: better-auth with the organization plugin. `initAuth()` is in `@guildkit/db`, the backend's instance is `auth` in `projects/backend/src/lib/auth.ts`, and the frontend's client is in `projects/guildkit/src/lib/auth/client.ts`. Users have a `type` (`candidate` | `recruiter`) and a `role` (`projects/db/src/auth/roles.ts`). Recruiters belong to organizations.
- **Web API**: Each endpoint is a Route Handler in `projects/backend/src/app/api/**/route.ts`, served under `/api`.
  - Route Handlers use `prisma` and `auth` from `projects/backend/src/lib/`. They are module-level variables; `prisma` forwards to a PrismaClient created for each request because Cloudflare Workers cannot reuse a DB connection across requests.
  - Protected Route Handlers call `requireAuthAs(request, "recruiter" | "candidate" | "any", options)` from `projects/backend/src/lib/auth-guard.ts`. It returns `{ user, session }`, or an error `NextResponse` (401) that the handler must return as is. It also sets the active organization of recruiters.
  - Validate input with Zod schemas from `@guildkit/shared/zod` or `projects/backend/src/schemas/`, and return `{ errors: flattenError(error) }` with status 400 when validation fails. Other errors return `{ code, message? }`.
  - Document each Route Handler with the JSDoc tags of [next-openapi-gen](https://github.com/tazo90/next-openapi-gen) (`@tag`, `@path`, `@query`, `@body`, `@response`, `@add`, …). Schema names in the tags refer to Zod schemas in `projects/shared/src/zod` or `projects/backend/src/schemas`. Do not use commas or colons in the descriptions of `@response` and `@add`.
  - The `sync` script of the backend generates the OpenAPI spec (`projects/backend/openapi/openapi.json`), and the `sync` script of `@guildkit/client` generates its types from the spec with openapi-typescript.
- **Component split**: Interactive components are split into `X.tsx` (server) and `X.client.tsx` (client), e.g. `JobEditor`, `OrgEditor`, and `app/auth/page.client.tsx`.
- **Errors**: Thrown errors include a unique code such as `GK-9JFB6` to make them traceable.

### Quick Start

1. `cp .env.example .env` (required: setup scripts need `SERVER_ENV`)
2. Start the Podman daemon
3. `mise install`
4. `pnpm run build`
5. `pnpm run dev`

### Commands

Run tasks with `pnpm run <script>` in a shell where mise is activated, or with `mise exec -- pnpm run <script>`, so that the tools and `.env` from `.mise/config.toml` are loaded. Root scripts (`dev`, `build`, `preview`, `deploy-preview`, `test`, `lint`, `fix`, `sync`) run the same-name script in each project with `pnpm run -r --if-present`. pnpm does not install the dependencies before running scripts (`verifyDepsBeforeRun: warn` in `pnpm-workspace.yaml`), so run `pnpm install` when it warns that `node_modules` is out of sync.

- `mise install` - Install all dependencies, including npm dependencies. `pnpm install` runs the root `prepare` script, which starts the containers and then runs `sync` to create the generated files. pnpm skips `prepare` when `node_modules` is already up to date, so do not rely on it to create the generated files.
- `pnpm run dev` - Start dev servers including the frontend (port 3000), the backend (port 3001), database server, and object storage server.
- `pnpm run build` - Build the libraries with tsdown, and the frontend and the backend with `vite build`.
- `pnpm run preview` - Build application in the `development` mode and serve the build output on the local workerd runtime.
- `pnpm run deploy-preview` - Run `scripts/deploy-preview.nu` for the preview workflow. It deploys the build output as a Cloudflare Worker Preview named after the PR author's GitHub username in `PR_AUTHOR` (without a trailing `[bot]`), so each user has a fixed Preview URL (`cf previews deploy --prebuilt`). Then it sets the Preview's `DATABASE_URL` and `BETTER_AUTH_URL` secrets (`wrangler preview secret bulk`) and comments the Preview URLs on the PR `PR_NUMBER` (`gh pr comment`). Run `pnpm run build` with `CLOUDFLARE_PREVIEW_BUILD=true` first, so that the build output is a Preview build. It also requires `DATABASE_URL` and `GH_TOKEN`.
- `pnpm run lint` - Run `tsc --noEmit` and ESLint.
- `pnpm run fix` - Fix linting issues.
- `pnpm run clean` - Delete the Docker containers and gitignore'd files except for .env and mise.local.toml.
- `pnpm run refresh` - Recreate the Docker containers and pnpm-lock.yaml, and update pnpm.
- `pnpm run ai-postedit` - Syncs generated files, then runs the project lint scripts, `tsc --noEmit`, `eslint --fix`, and the project fix scripts. Use it to check your edits.
- `pnpm run sync` - Generates the files the other scripts need. Run it at the root or in each project. The `dev`, `build`, and `lint` scripts of each project run it.
  - `@guildkit/shared`: Generates the currency list if it does not exist, and builds the library, which the `sync` scripts of the other projects import.
  - `@guildkit/db`: Builds the library, which the `sync` script of the backend imports.
  - `@guildkit/backend`: Generates the enum schemas, regenerates the Prisma clients, better-auth schema, and vinext type definitions, applies migrations, seeds dev data, and generates the OpenAPI spec.
  - `@guildkit/client`: Generates the types from the OpenAPI spec and builds the library.
  - Frontend: Regenerates the vinext type definitions.
- `pnpm run seed` (in `projects/backend`) - Seeds the DB. It only runs when `SERVER_ENV` is `development`, `demo-production`, or `demo-preview`, and only when the DB is empty.
- `pnpm run deploy` (in `projects/backend`) - Builds and deploys the backend to Cloudflare Workers.

There is no test suite yet. The root `test` script exists, but no project defines a `test` script.

### Environment variables

- `SERVER_ENV` is required by the setup and sync scripts. Copy `.env.example` to `.env` for local development (`SERVER_ENV=development`). mise loads `.env` automatically.
- On Cloudflare Workers, set the secrets declared in `cloudflare.config.ts` as the Worker's secrets. The following describes the frontend's `cloudflare.config.ts`. `SERVER_ENV` is not a secret: `cloudflare.config.ts` embeds it into the Worker as `preview` for Preview builds (`pnpm run deploy-preview`) and `production` for the other builds. In the `development` mode (`pnpm run dev` and `pnpm run preview`), it is loaded from `.env`. `cloudflare.config.ts` embeds `BETTER_AUTH_URL` as `https://demo.guildkit.net` only in the `production` mode. Otherwise it is a secret, loaded from `.env` in the `development` mode. Worker Previews take their secrets from the Preview base config, and `pnpm run deploy-preview` sets the PR's Neon branch as `DATABASE_URL` and the Preview URL as `BETTER_AUTH_URL` of each Preview. Since the Worker cannot start without `BETTER_AUTH_URL`, `pnpm run deploy-preview` sets a dummy `BETTER_AUTH_URL` in the Preview base config and the existing Preview before the deployment. `pnpm run deploy-preview` requires `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`.
- In `development`, the root `prepare` script starts Postgres and RustFS (an S3-compatible store) with `compose.yaml`. The RustFS image built from `containers/storage/Dockerfile` already has the `guildkit` bucket. The RustFS console is at http://localhost:9001.
- The backend's `cloudflare.config.ts` embeds `SERVER_ENV` like the frontend's, and declares the other variables as secrets in all modes. Outside the `development` mode, it also declares `STORAGE_BUCKET` and `CLOUDFLARE_ACCOUNT_ID` for Cloudflare R2. The backend is not deployed as Worker Previews.
- The bindings are available as `process.env.*` with the `nodejs_compat` compatibility flag.

## Instructions

- Wording: An **organization** is the hiring company. A **recruiter** is a staff user who belongs to an organization. Use **employer** only when you mean both.
- Use the `@/` path alias for `projects/guildkit/src` and `projects/backend/src`, and include the `.ts`/`.tsx` extension in import paths.
- Do not edit gitignored files.
- After you update the code, check AGENTS.md and find if there is anything outdated. If there is any outdated content, update or delete it.
- Split Git commits by step. Keep each commit's diff readable: if stylistic changes (formatting, renames, reordering) would make the diff hard to read, put them in separate commits from the functional changes.
- When you rebase onto the `main` branch, do not fold the changes needed to adapt to `main` into the existing commits. Put them in separate new commits so that the user can fixup them into the original commits later.
- Commit changes to the following files in separate commits from other changes:
  1. Lock files of the package managers (e.g. `pnpm-lock.yaml`, `skills-lock.json`)
  2. The `allowBuilds` section of `pnpm-workspace.yaml`
  3. Database migration files
  4. Other machine-generated files
